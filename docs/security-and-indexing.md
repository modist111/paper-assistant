# 安全与索引可靠性：实现、验证与面试讲解

## 本次解决的问题

旧版 API 使用 Service Role 直接查全表。数据库虽然有 RLS，但 Service Role 会绕过它；
知道论文 UUID 的调用者可能读、问答或删除别人的论文。上传后的索引依赖 after()，
进程中断没有持久任务，批次写入失败又可能留下不完整向量。

现在每个论文 API 都先通过 Supabase Auth 的 getUser() 验证会话，并固定过滤当前用户 ID。
向量搜索改用用户会话，因此即使绕开前端调用 RPC，数据库仍会执行 RLS。
Service Role 留在服务端，仅用于经过归属检查的写操作和 worker RPC。

入口文件：

- src/lib/auth/user.ts：验证用户身份。
- src/middleware.ts：刷新会话并保护上传、论文、聊天页面。
- src/app/api/papers、upload、chat：检查归属，拒绝跨账号访问。
- src/lib/ai/retrieve.ts：用户会话 + RLS 的检索。
- supabase/migrations/002_auth_and_index_jobs.sql：权限、任务表、事务函数。
- src/lib/indexing/jobs.ts 与 scripts/index-worker.ts：worker 和租约。

## 数据流和一致性

1. 登录用户上传 PDF；服务器验证文件类型、大小和 PDF 文件头。
2. PDF 写入私有 papers bucket，以用户 UUID 为路径前缀。
3. create_document_with_index_job() 在一个事务内创建论文和 queued 任务。
4. after() 尝试快速启动第一轮；独立 worker 持续扫描任务并接手自动重试和中断恢复。
5. worker 使用 SELECT FOR UPDATE SKIP LOCKED 领取任务，得到唯一 lease_token。
6. 租约有效期为两分钟，worker 每 30 秒心跳续约，解析、分块、向量化时记录进度。
7. 全部向量准备好后，finish_document_index_job() 锁任务行、校验令牌和过期时间，
   在一个事务中替换文本块并标记论文 ready。
8. 暂时错误使用 10、20 秒退避，单轮最多三次；401、403、维度不匹配等配置错误直接失败。
9. 进程死亡后，其他 worker 可在租约过期后接手；到达最后一次的中断任务会被标记 error。
10. 用户可以在详情页重新处理失败或中断任务；旧 worker 的令牌不能覆盖新任务。

必须持续运行 npm run worker，或由部署平台的进程管理器运行该命令。
仅运行 Web 进程时，after() 能启动首轮，但无法保证队列恢复和定时重试。

## 面试问答

### 1. 认证与鉴权有什么区别？

认证回答“请求是谁发的”，鉴权回答“这个人能操作哪些数据”。我用 Supabase getUser()
在服务端验证会话，再在查询中固定 user_id。前端隐藏按钮只改善体验，不能作为权限边界。

### 2. UUID 难猜，为什么还要检查归属？

UUID 只是资源标识，不是授权凭证。ID 可能从 URL、日志、分享或响应里泄露。
我的详情、问答、删除和重试都会按 id + 已验证的 user_id 查询；查不到统一返回 404，
不向外人区分“资源存在但不属于你”与“不存在”。未登录返回 401。

### 3. 有 RLS 为什么仍然可能越权？

RLS 约束的是数据库当前角色。Service Role 有绕过 RLS 的能力，不能因为表里定义了策略
就认为所有请求安全。我让普通检索使用用户 JWT，写入端使用 Service Role 时另做归属校验，
并撤销浏览器对论文、向量和任务表的直接写入，防止客户端改 user_id 或 Storage 路径。

### 4. 为什么服务端用 getUser()，不是直接相信 cookie 或 getSession()？

客户端传来的 cookie 和 user_id 都不可信。getSession() 主要读取已有会话，不能代替身份验证；
这里用 getUser() 向 Supabase Auth 验证身份。服务端写入的 user_id 取自验证结果，不取自请求体。

### 5. 为什么 after() 不足以构成可靠后台任务？

after() 让响应发出后继续执行回调，但任务仍属于 Web 实例。实例重启或执行时间到期会中断它。
我先把任务写进 PostgreSQL，再由独立 worker 领取；after() 只用于减少第一轮等待。
即便它没有执行，队列记录还在，worker 能从 Storage 重新下载 PDF 并恢复。

### 6. 为什么选择 PostgreSQL 任务表，而不是 Redis/RabbitMQ？

项目已经使用 PostgreSQL，当前任务规模不大。数据库事务能原子创建论文与任务，也能原子发布索引，
运维依赖少。使用 SKIP LOCKED 避免多个 worker 等待同一任务。若任务量、吞吐或调度需求明显增大，
再评估专用消息队列；切换时仍然需要幂等、重试和结果一致性设计。

### 7. 为什么锁要有过期时间和心跳？

如果只把任务标记为 processing，worker 宕机后它会永远卡住。租约规定领取者的有效时间，
心跳证明它仍在工作。停止心跳后租约过期，其他 worker 才能重新领取。
我选两分钟租约和 30 秒心跳，同时限制任务处理约五分钟，避免网络卡死永久续约。

### 8. 旧 worker 又恢复执行，会不会覆盖新结果？

会有这种风险，所以仅有过期锁还不够。每次领取生成新的 lease_token，发布时在事务内锁住任务行，
同时校验状态、令牌和过期时间。新任务一旦换令牌，旧任务即使拿到了模型响应，也不能发布。
这里是等值校验的所有权令牌，不声称实现了跨多个外部系统的全局递增 fencing 序列。

### 9. 如何避免重试生成重复向量？

处理阶段只在内存准备文本块和向量，成功时以事务替换整篇文档的索引。
删除旧块、插入新块、修改 ready 状态是一次提交；任一步失败会回滚。
同一个任务完成后再次发布会因状态和令牌校验失败而被拒绝。

### 10. 这是 exactly once 吗？

我不会这样描述。任务可能被重新执行，模型调用也可能重复计费；采用的是允许重复尝试的处理方式，
通过租约令牌与事务确保数据库最终只发布一份完整结果。外部 API 调用与 PostgreSQL 不是同一个事务，
不能保证跨系统“恰好一次”。

### 11. 所有错误都重试吗？

不。网络错误和暂时服务错误通常值得重试，使用有上限的退避；鉴权失败、配置错误、维度不匹配
或无法解析的文件继续重试通常无益。修复配置后，用户可以手动开始新一轮任务。
错误分类目前按 HTTP 状态和已知解析错误判断，实际使用中应依据失败样本继续完善。

### 12. 如何验证安全和可靠性，而不是只“写了代码”？

我分两层：接口测试检查请求身份与资源归属，且拒绝后不会调用模型；数据库测试真实执行迁移，
检查 RLS、权限、事务回滚、租约过期和旧任务发布。最后在部署环境用两个账号做端到端验收，
并模拟 worker 停止后重新启动。只有实际完成的验收才写成项目成果。

### 13. 文件存储和数据库怎么保持一致？

它们不能直接共享数据库事务。上传先写 Storage，再原子创建论文与任务；如果建库记录失败，
尝试补偿删除文件。删除先取消任务并删除元数据，之后清理对象；对象清理失败会记录日志，
不会让晚到的 worker 复活论文。仍可能出现无元数据的孤儿文件，后续可加定期对账清理。

### 14. 这套方案还有哪些边界？

大文档的完整向量暂存在 worker 内存里，超大文件需要流式暂存或 staging 表；
目前没有公网网关级限流与用户计费配额，也没有声称完成压力测试。
它解决的是项目当前具体的身份隔离、失败重试和进程中断恢复问题。

## 60 秒项目讲解示例

“我把论文问答从单用户演示改成了按账号隔离的应用。之前 Service Role 查询会绕过 RLS，
我补了服务端身份校验、资源归属校验和数据库写权限限制，向量检索也使用用户会话。
索引原先是响应后的进程内任务，重启会卡在处理中；现在用 PostgreSQL 存储任务，独立 worker
以租约和心跳领取，失败退避重试，并用令牌阻止旧任务回写。向量与 ready 状态在同一事务发布，
避免半成品和重复向量。我用真实 SQL 的隔离测试验证了权限、任务恢复和回滚行为。”

使用这段话前，应亲自跟踪一次请求，能打开相关代码解释每一步，且只描述已经执行通过的测试。
